# 05 · 复盘

## 1. 最难的一个问题：预算判断该留在模型里，还是写进代码里

最初的直觉是"让模型自己判断超没超预算"——听起来最符合 ReAct 的精神。写完第一版就发现问题：
模型要判断，就得先知道费用；而费用一旦由模型自己算（"素材 4 条 2.4，脚本 3.0……"），
它就有机会算错，还错得很有说服力。

最后切成了三段：

1. **算钱是工具的事**（`estimate_cost` 用同一张单价表）；
2. **比较是模型的事**（12.0 > 10.0，退一档）——这才是"决策"；
3. **验收是代码的事**（`save_plan` 二次核算，差 0.01 就拒；`_finish` 校验超预算/超工时不许 `COMPLETED`）。

这个切分让我第一次真正理解"Agent 里什么该交给模型"：**把模糊判断交给模型，把确定性计算留给代码**。
反过来说，如果哪天模型把 12 和 10 比错了，`save_plan` 会拒——错误被限制在一处，而不是扩散到报价单。

## 2. 第二难：怎么诚实地处理"没有密钥"

我没有模型密钥，但这题的核心又是"模型决策"。两条路：

- 只交真实模型路径 → 评审第一步卡在环境变量，整个仓库变成"看代码想象结果"；
- 只交 mock → 容易被说成"固定分支假装 Agent"。

我选了第三条：两个规划器共享同一 `decide(ctx)` 接口，mock **读真实工具返回值**做决策，
并把边界写死在文档里（`docs/03` 第 5.2 节：mock 证明流程，不证明模型效果）。
同时把真实模型做成可替换的一层，拿到密钥只需换三个环境变量。

这件事的收获是：**"没做"和"没验证"要在文档里显式出现**。评审扣分不会因为承认缺口，
但会因为有缺口却写得像做完了。

## 3. 返工最痛的一处：续跑

`case-03` 第一次跑出来是"补齐预算后仍然 `NEED_INPUT`"，而且是两条一模一样的 `request_input`。
原因很蠢：`resume` 时我从 `state.json` 恢复了任务，把 CLI `--set` 的新预算覆盖掉了。
教训是**检查点的语义要明确**：它保存的是"进度"，不是"输入"。输入永远以调用方为准。

修完之后顺手确认了另一件事：续跑不能重跑已成功的步骤。`scratch.materials` 留在检查点里，
续跑直接复用，所以 `case-03` 只花了 7 步就把整条链路走完，而不是从头再检索一遍。

## 4. 幂等这件事比想象中细

第一版用 `uuid4` 生成 plan_id，第二次执行就多出一份"新方案"，内容一模一样。
换成内容指纹（topic + 档位 + 素材 + 费用）之后，重复执行自然收敛到同一个文件。

但马上遇到新问题：**实施例之间互相污染**。`gen_examples.py` 第一次跑，case-01 就 `deduped: true`，
因为上一轮试跑存过。于是加了"先清空方案目录 + 固定执行顺序"，并让 case-07 故意去撞 case-01 的指纹——
"重复执行"这个验收点才真的被验证，而不是被环境巧合掩盖。

## 5. mock 规划器的三个真实弱点（比优点更值得记）

1. **关键词抽取靠标签命中**：`case-09` 最初主题是"展会现场快剪"，一个标签都没命中，
   直接掉进"素材 0 命中"分支。真实模型不会犯这个错，但这也说明 mock 的策略上限很低。
2. **不会主动换策略**：素材只拿到 1/4 时，它选择"按 1 条重算"而不是"再检索一次补足"。
   我保留了前者，因为它不会把工具抖动放大成重试风暴；但真实模型完全可能选后者，两者都对。
3. **不会反思**：同一档位失败两次就降级，没有"换个 tone 再试"这类更细的动作。
   上限 12 步的前提下这是合理取舍，但它确实不是"会思考"。

写这些不是为了自贬，而是因为题目明确说"Mock 只验证流程，不证明真实模型决策效果"——
我把这句话落成了具体的三条，而不是文档里一句免责声明。

## 6. 学到的三件事

1. **Agent 的可靠性来自约束，不来自提示词**。步数上限、二次核算、收尾校验，这三道闸门
   在没有模型的情况下就已经把"假完成"挡住了；换任何模型都不用重写。
2. **可审计性要设计进去**。`decision_basis` 必须带数字（"12.0 超预算 10.0"），
   否则事后没人能判断这是"决策"还是"文案"。这一条我在写 planner 时就要求了。
3. **验证材料要能一键重跑**。`gen_examples.py` + `pytest` + `verify_submission.py` 三条命令，
   比截图和视频有说服力得多；截图会过期，命令不会。

## 6.1 最后悔的一件事：先写代码，后对清单

代码跑通、文档写完，我才回头把题目逐条对着仓库核了一遍，结果发现三处硬缺口：
交付结果缺"任务计划"和"步骤状态"、续跑其实是重跑、LLM 路径压根没跑过。

前两处都是"功能上能做，但没按交付形态暴露"，第三处是"写了但没验证"。
如果一开始就把题目要求抄成一张勾选表（计划/步骤/费用/方案/未完成原因 + 5 条必须验收），
写第一行代码前就能把这些位置留出来。**自查清单比写完再补便宜得多**——
补这三处花了近 40 分钟，而列清单只要 5 分钟。

另外有个意外收获：为了验证 LLM 路径而起的本地兼容端点（`scripts/fake_llm_server.py`），
顺手把三个只在"换实现"时才暴露的坑炸了出来（收尾校验读私有状态、提示词花括号、
本地端点被代理劫持）。这印证了一件事：**接口换一个实现，比在原实现上加十个测试更能发现问题**。

## 6.2 最后一轮自查抓到的四类问题

提交前又按规范逐项过了一遍，抓到的都不是"功能错误"，而是**会被评审直接看见的工程痕迹**：

1. **重复代码**：`src/agent.py` 里 `chosen_variant` 的赋值写了两遍；
   `tests/test_tools_cost.py` 末尾整段重复了两个测试类——后定义的类覆盖前一个，
   前面那份其实是死代码，`pytest` 也不会多收用例。
2. **重复文档**：`docs/05` 的"最后悔的一件事"整节写了两遍；`docs/04` 还留着
   "待本人确认"这种只有作者本人能填的占位符。对评审来说，这等于把"没写完"直接交上去。
3. **可复现性**：README 的运行命令没带 `--now`，而输入里的截止时间是 2026-11-02；
   过了这个日期再跑，"可用分钟"会变成 0，正常用例会变成预算/工时不足。
   加上 `--now` 并把落盘路径改成相对路径后，命令才能长期复现。
4. **换规划器丢状态**：LLM 规划器的 `result.rejected` 是空的——被否方案只记在 Mock 的
   scratch 里。改成 Agent 侧统一记账后，`case-10` 也能看到 "full 12.0 超预算 10.0"。

这四类问题有个共同点：**它们不影响"跑通"，但影响"可交付"**。
以后我会在提交前固定跑一遍 `verify_submission.py`，把"目录/字段/占位符/实施例状态"
这类机械检查交给脚本，而不是靠眼睛。
